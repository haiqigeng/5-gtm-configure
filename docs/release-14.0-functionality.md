# configure-gtm product functionality audit

Audit date: **2026-10-14**. Scope: the 14.0 candidate implementation, its advertised reference routes, deterministic tests, and independently inspected saved web objects. Official sources below were checked on this date unless stated otherwise. This report contains no client identifiers or user data and can be published with the release documentation.

## What the evidence establishes

The product configures an explicitly approved native object graph and checks the saved result. Its vendor guides help select and inspect an implementation. A vendor's appearance in a guide is not an executable vendor integration or a runtime certificate.

| Evidence level | Meaning |
| --- | --- |
| **Guide** | A documented route to investigate; the current product/template, exact fields, approved source and adapter still need inspection. |
| **Deterministic** | Code validates a represented invariant, resolves an actual native field, or compiles a supported native binding. This establishes configuration consistency. |
| **Offline saved graph** | A test executes through a fake backend, native comparison and checkpoint/no-op logic. It exercises behavior but does not call GTM or a vendor. |
| **Authentic source** | A pinned official template or inspected native representation establishes actual field names and types. |
| **Live saved object** | An independent GTM read establishes that GTM retained the specific configuration. |
| **Runtime** | A real browser/server event, resolved values, outgoing request and relevant response demonstrate execution. **No new runtime proof was established by this audit.** |

Assertions, approval hashes and a successful mock cannot upgrade one level to another. Installed template source is authoritative for its native identity and parameter schema; it does not prove its SDK executes successfully.

## Corrections and executable mechanisms

**RUN10: browser Ads enhanced conversions.** The later authenticated read on 2026-10-14 at 15:51 UTC retained a native Ads Conversion Tracking tag (`awct`) with a `LIST`/`MAP` `eventSettingsTable` row whose `parameter` is `user_data` and whose `parameterValue` references the native User-Provided Data variable. An earlier missing field and discarded guessed controls did not establish permanent lack of support. The current official procedure expressly permits event-specific `user_data`. The candidate now binds the exact inspected row and semantic name, requires the native UPD source, and rejects a different row, duplicate binding or arbitrary field path. The purchase-only scope is retained. [Google Ads enhanced conversions](https://support.google.com/google-ads/answer/13262500?hl=en).

The sanitized provenance fixture records the actual shape; it contains synthetic values. The raw authenticated readback remains a local audit artifact. Neither proves variable resolution, hashing, request transmission, account activation, match quality or received conversions.

**GA4 collection and Ads transport are separate approved features.** Current GA4 instructions also select a native UPD variable in Event Parameters `user_data`; an obsolete dedicated-selector assumption was removed. The same physical event field can serve separately authorized purposes. The contract binds the product, capture timing, native consumer, UPD reference, hashing owner, consent and external activation. It does not permit arbitrary PII in ordinary GA4 parameters. Google-tag server transport uses the documented Configuration `user_data` carrier; an event-scoped GA4 sender uses Event Parameters. [GA4 user-provided data](https://support.google.com/analytics/answer/14179229?hl=en), [server Ads user data](https://developers.google.com/tag-platform/tag-manager/server-side/ads-user-data).

**RUN11: compatible shared ownership.** A compact preparation compiler now moves repeated approved scalar GA4 Event fields to one native Event Settings variable (`gtes`). It verifies the actual untransformed version-2 DLV source, shape and missing behavior, source-event trigger opportunity, destination, consent policy, lifecycle, blocking gates and native firing option. Only compatible authorized create/update consumers participate; generated authority is limited to their requirements. Field mappings resolve the native storage owner, approvals bind the resulting payload, and local differences retain their event owner. [Event Settings](https://support.google.com/tagmanager/answer/13438771).

Behavior tests exercise **23 consumers × 6 common fields**, unchanged effective payloads, incompatible scopes, exact field ownership and approval, fresh preparation against saved inventory, and a completely new run with no additional writes. This is offline proof. The independently inspected earlier live configuration still contained repeated local rows; it did not contain the candidate's new shared variable.

The compiler shares the intersection within one compatible consumer group. If A and B have `x,y` and C has only `y`, it shares `y`; `x` remains local to A/B. One native settings reference per consumer prevents naive overlapping group assignment. Existing authored inheritance/overrides remain intact. This mechanism does not promise to minimize every arbitrary overlapping field graph or consolidate identities, user data, item arrays, transformations or non-Google settings.

**RUN12: consent must describe actual gates.** Native Google consent behavior changes collection/request handling. GTM Additional Consent Checks and blocking triggers determine eligibility. Receiving Google's transported state is not itself an extra configured eligibility gate. The candidate derives the actual gates from native objects and scoped consent policies, rather than copying authored booleans about double gating. Tests cover the strict/advanced product rules and the actual native eligibility controls. [GTM consent checks](https://support.google.com/tagmanager/answer/10718549?hl=en), [server consent](https://developers.google.com/tag-platform/tag-manager/server-side/consent-mode).

| Server-only implementation | Requires the named request protocol, claiming Client, Event Data shape, transformations and exact receiving template. No browser HTML/Custom JavaScript route can substitute for a server implementation. |
| Unlisted vendor / affiliate partner | General configuration workflow remains available, conditional on current official partner/product instructions and exact installed fields. No universal vendor schema, consent mapping, order identity or dedup contract is asserted. |
| Setup/cleanup sequencing | Native setup/teardown references and failure flags have offline adapter/roundtrip tests for otherwise represented execution units. **Setup/cleanup-only lifecycle units remain unsupported by the current execution policy model.** Do not advertise blanket sequencing semantics: Google bypasses ordinary trigger eligibility for sequenced tags. [Tag sequencing](https://support.google.com/tagmanager/answer/6238868). |

The workflow supports authorized web, server and connected pipeline modes. Web-only transport records receiver work as an external dependency. Pipeline mode can validate the represented sender/Client/Event Data/receiver graph. Neither mode certifies real delivery. Tracking-plan design, general cleanup, runtime QA, infrastructure deployment, container publication and version creation remain outside this skill's scope.

For a future Ads-only server `user_data` route, each effective downstream tag, including an existing
GA4 forwarder, needs its separately approved matching feature or a proved non-transmission
disposition. Google's current guidance states that an unchecked GA4 property UPD checkbox prevents
transmission to that property even when the Google tag still collects data. An inspected applicable
property state is legitimate evidence; a scoped Transformation is another supported disposition
when needed. The validator proves declared Ads receiver/field-flow bindings and catches explicit
unauthorized native identity fields. It does not discover or simulate every implicit automatic
Event Data forwarding path. Selection therefore depends on inspected native handling, applicable
property state or exact scoped exclusion, with actual requests checked separately. This is a
conditional capability; the audited live browser configuration has no server Ads deployment.
[GA4 property collection controls](https://support.google.com/analytics/answer/14077171?hl=en-GB),
[server forwarding guidance](https://developers.google.com/tag-platform/tag-manager/server-side/send-data),
[scoped Transformations](https://developers.google.com/tag-platform/tag-manager/server-side/transformations).
